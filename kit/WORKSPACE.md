# Give the work a useful home

Use this when the task needs files or a checkpoint beyond the current answer.

## Start from the existing workspace

Read its entry and working instructions. Find the current result and next
action before reorganising anything. Reuse its note, issue, notebook or README.
Keep its governing contract and authoritative records. An optional PAPP summary
can point to them; it should not become a competing source of truth.

## For a new workspace

Use the location the user supplied. If the location is missing and matters,
ask for it while preparing work that does not depend on that choice. When
creating the project is authorised and file tools are available, create the
project folder and one useful project note, such as `PROJECT.md`. Choose a
different name when it fits the user's environment.

That note connects the goal, materials/assumptions, work and checks, current
conclusion/limits, owner and next action. Add the pertinent working agreement
or a resolvable reference to this guide. State the reference base and required
access if it lies outside the project. A dependency on the kit is not a
self-contained handoff.

If the folder must carry its instructions independently of this conversation,
include `PAPP.md`, `CONTRACT.md` and `COMPATIBILITY.md`, or a sufficient
self-contained working agreement in the note. Add selected modules only when
their guidance must travel too. Preserve their relative paths and include or
resolve their necessary references. Check those references from the delivered
folder. Identify the guide being used. This minimum does not require copying
`START_HERE.md`; if it or another guide travels, its necessary links must work too.

This is the minimum needed to carry working instructions. Before
redistributing a partial copy, confirm the rights applicable to those files
and retain all required copyright and permission notices, including the
chosen licence when required. Operational sufficiency does not itself grant
redistribution rights. When redistributing copies or substantial portions of
this kit's original guidance, include its `LICENSE` and preserve applicable
notices. Linked third-party sources retain their own rights.

Create `src/`, `tests/`, `sources/`, `data/` or `outputs/` when a real file needs
that home. These are examples, not a compulsory tree. Keep supplied originals
distinct from transformed data or generated results when their use requires it.

## Resume and update

Open the current note. Inspect its linked result and relevant qualifications.
Continue the next authorised action; do not repeat completed work merely because
the chat is new. After meaningful work, update only the relevant result and
checkpoint. Retain a superseded interpretation with a pointer to its successor.
If an upstream home belongs to someone else, qualify the affected use and refer
to its owner rather than changing that record without authority.

Keep the current checkpoint brief: qualified result, decisive conditions and
limits, unresolved matters and next authorised action, with links to necessary
evidence and history. Preserve qualifications and accessible references before
moving older detail out of the current note, and identify its successor.
Shortening the note must not strengthen the conclusion.

For a checkpoint with concurrent writers, reread the current state and reconcile
intervening changes before saving. Use the tool's version/conflict checks or
coordinate writes so another update cannot be silently overwritten; rereading
alone does not prevent changes between reading and saving. Preserve conflicting
interpretations and refer unresolved meaning to the responsible owner.

With no file tools, return the useful content and a checkpoint the user can
save. Say that it was returned, not saved. For a two-line explanation that
needs no later handoff, an inline answer is enough.

See the [filled note](examples/PROJECT_NOTE.md). It is an illustration, not a
mandatory template or an executed research result.
